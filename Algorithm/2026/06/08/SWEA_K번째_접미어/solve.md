### SWEA 1256 [K번째 접미어](https://swexpertacademy.com/main/code/problem/problemDetail.do?contestProbId=AV18GHd6IskCFAZN) (Java)

> **날짜:** 2026년 06월 08일 <br>
> **알고리즘:** 정렬, 문자열, 트라이 <br>
> **언어:**  Java <br>
> **핵심 키워드:** 정렬 조건, 트라이

## 📌 문제 개요

영어 소문자로 구성된 하나의 문자열이 주어졌을 때, 해당 문자열에서 파생되는 모든 접미사(Suffix)를 사전순으로 정렬하고 $K$번째에 위치하는 접미사를 통째로 출력하는 문제다.

* 문자열의 최대 길이가 400으로 매우 작다는 특징이 있다.

---

## 💡 풀이 핵심 (Core Logic)

### 1. 객체 풀링(Object Pooling) 기반 경량 Suffix 구조체

* `static block`을 통해 사용할 최대 크기(`MAX_SIZE = 400`)만큼의 `Suffix` 객체를 프로그램 시작 시 단 한 번만 생성하여 메모리에 고정해 둔다.
* 매 테스트 케이스마다 `new` 연산자로 힙(Heap) 영역에 인스턴스를 생성하는 행위를 원천 차단하여 메모리 사용량을 줄인다.

### 2. O(1) 입력 단계 역전 트릭 (Loop Elimination)

* 문자열 입력 루프 도중 `suffix[total].len = total;`로 인덱스 값을 그대로 사용한다.
* **수학적 원리:** 문자열 입력이 전진할수록(`total` 증가), 남은 접미사의 실제 길이는 반대로 줄어든다. 즉, **시작 인덱스가 큰 접미사일수록 실제 길이는 짧아진다는 반비례 관계**를 역이용한다.

### 3. 인덱스 기반 포인터 비교 (Zero-Copy String)

* `compareTo` 구현 시 실제 `String.substring()`을 수행하지 않고, 공유 전역 정수 배열인 `input`의 두 시작 지점(`this.start`, `o.start`)을 직접 타고 들어가 글자 단위 포인터만 전진시키며 크기를 비교한다.

## 📊 풀이 방식 비교 ( 트라이 vs 커스텀 정렬 )

| 비교 항목 | 트라이 (Trie) | 접미사 배열 기반 커스텀 정렬 |
| --- | --- | --- |
| **구조의 성격** | 메모리 집약형 트리 (Tree Layout) | 경량 포인터 배열 (Pointer Array) |
| **공간 복잡도** | $O(\text{총 글자 수} \times \Sigma)$ (약 $80,205 \times 26$ 크기의 고정 2차원 배열 필요) | $O(N)$ (원본 크기인 400짜리 1차원 구조체 배열로 종결) |
| **초기화 비용** | 테케마다 사용된 모든 노드 초기화가 필요함| 입력받은 길이만큼만 부분 정렬 수행 |
| **탐색 메커니즘** | 루트부터 자식 노드를 카운팅 하며 경로 추적 | 사전순 정렬이 끝난 배열의 k - 1번 인덱스 명찰 확인 후 출력 |
| **이 문제에서의 결론** | 고유 부분 문자열이 아닌 전체 접미사 출력이라 과스펙 및 비효율 | 데이터 입력과 정렬 매핑을 O(1)에 엮은 정렬 방식이 최적 |

## 🧠 회고 및 결론

K번째 접미어 문제를 접하고 가장 먼저 떠올린 자료구조는 트라이(Trie)였다. 모든 접미사를 트라이에 삽입하면 무거운 문자열 객체를 직접 생성하지 않고도 자식 노드 탐색을 통해 자연스럽게 사전순 정렬을 수행할 수 있기 때문이다.

그러나 예상보다 메모리 사용량이 과도하게 높게 측정되었고, 원인을 분석한 결과 이 문제의 출제의도는 트라이가 아님을 깨달았다. 트라이는 `(최대 발생 가능한 노드 수) × 26` 크기의 고정 2차원 배열 공간을 요구하므로, 단순 접미사 정렬만 수행하는 이 문제의 요구사항에는 불필요한 메모리 낭비가 심했던 것이다.

이 문제의 결정적인 힌트는 다루는 대상이 '모든 부분 문자열'이 아닌 오직 '접미사(Suffix)'라는 점에 있었다. 접미사는 시작 인덱스(`idx`) 정보만 알고 있으면 원본 배열을 참조하여 해당 문자열의 형태를 즉시 파악할 수 있다. 이 고유한 특징을 활용하면 무거운 문자열을 복사하거나 생성하지 않고도 포인터 이동만으로 사전순 비교 및 정렬을 수행할 수 있다.

결국 이 문제의 정해는 접미사의 인덱스 특징을 극한으로 활용하여 공간 오버헤드를 줄이는 **접미사 배열(Suffix Array)** 관점의 정렬 최적화였다.
