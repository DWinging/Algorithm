### SWEA 1795 [인수의 생일 파티](https://swexpertacademy.com/main/code/problem/problemDetail.do?contestProbId=AV4xuqCqBeUDFAUx) (Java)

> **날짜:** 2026년 5월 12일 <br>
> **알고리즘:** 다익스트라(Dijkstra), SPFA(Shortest Path Faster Algorithm) <br>
> **언어:**  Java <br>
> **핵심 키워드:** 다익스트라, 역방향 간선, 객체지향 모듈화, SPFA

## 📌 문제 개요

* $N$개의 마을에 사는 사람들이 $X$번 마을에 모여 파티를 하고 다시 각자의 마을로 돌아가야 한다.
* 마을 사이의 도로는 **단방향**이므로, 가는 길과 돌아오는 길의 최단 거리가 다를 수 있다.
* 각 사람들의 왕복 소요 시간(가는 시간 + 오는 시간) 중 **가장 오래 걸리는 시간**을 구하는 문제.

## 💡 풀이 핵심 (Core Logic) : 간선을 뒤집는 발상

이 문제의 가장 큰 함정은 "모든 마을에서 $X$로 가는 최단 거리"를 구하기 위해 마을 개수($N$)만큼 최단 거리 탐색을 돌리는 것입니다. 이렇게 하면 시간 초과(TLE)가 발생할 확률이 높습니다.

이를 해결하기 위한 핵심 발상은 그래프의 간선 방향을 뒤집는 것(Reverse Graph)입니다.

1. **정방향 그래프 (돌아오는 길):** $X$에서 시작해 모든 마을로 가는 최단 거리 탐색.
2. **역방향 그래프 (가는 길):** 간선의 방향을 `(u -> v)`에서 `(v -> u)`로 뒤집고 $X$에서 시작해 탐색하면, **단 한 번의 탐색으로 모든 마을에서 $X$로 오는 최단 거리**를 구할 수 있습니다.

결과적으로 $N$번 수행해야 할 연산을 단 **2번**의 탐색으로 압축하는 것이 1차적인 최적화 포인트입니다.

## 📊 풀이 방식 비교 (Dijkstra vs SPFA)

| 구분 | Dijkstra (PriorityQueue) | SPFA (ArrayDeque) |
| --- | --- | --- |
| **시간 복잡도** | $O(E \log V)$ | 평균 $O(V+E)$ ~ 최악 $O(VE)$ |
| **핵심 자료구조** | 이진 힙 (Binary Heap) | 원형 큐 (Circular Queue) |
| **노드 재방문** | **큐에서 여러 번 나옴.** 하지만 `visited[i]` 체크로 **간선 확장은 최초 1회만** 수행 (확정 이후 무시) | **큐에 여러 번 들어감.** 더 짧은 경로 발견 시마다 **연결된 간선을 다시 전부 탐색** (완전 재방문) |
| **오버헤드** | **높음.** 삽입 시마다 $\log V$ 정렬 발생 | **낮음.** $O(1)$ 삽입/삭제만 수행 |
| **음수 간선** | **처리 불가.** (확정 노드의 거리가 변하지 않는다고 가정하기 때문) | **처리 가능.** (갱신될 때마다 다시 큐에 넣어 확인하기 때문) |
| **실전 퍼포먼스** | 안정적이지만 정렬 비용 때문에 무거움 | 정렬 비용이 없어서 압도적으로 빠름 (단, 저격 데이터 주의) |

## 🛠 성능 최적화 인사이트 (Performance Insights)

### 1. 알고리즘 패러다임 비교: Dijkstra vs SPFA

단순 최단 경로 탐색을 넘어, 그래프 전체의 상태를 동기화해야 하는 '전파' 특성의 문제에서 자료구조의 선택이 성능에 미치는 영향을 확인했습니다.

* **성능 지표:**
* **Dijkstra (PQ):** 161ms / 34,056kb
* **SPFA (Deque):** **95ms / 27,008kb (시간 41%, 메모리 20% 절감)**


* **분석:** Dijkstra는 $O(E \log V)$의 확정적 안정성을 제공하지만, 모든 노드를 방문해야 하는 왕복 문제에서는 PriorityQueue의 정렬 오버헤드가 병목이 됩니다. 반면, SPFA는 정렬 비용을 제거하고 $O(1)$의 Deque 연산을 통해 갱신된 정보를 빠르게 전파하며 압도적인 퍼포먼스를 보여주었습니다.

### 2. 무의미한 탐색 제어 (Early Exit Condition)

다익스트라 수행 시, 우선순위 큐가 빌 때까지 반복하는 대신 **최단 거리가 확정된 노드의 수**를 추적하여 조기 종료 조건을 적용했습니다.

* **핵심 로직:** `total < n` (확정 노드 수 < 전체 노드 수)
* **인사이트:** 모든 노드의 최단 경로가 결정된 이후에도 큐에 남아 있는 중복 노드들에 대한 불필요한 힙(Heap) 연산과 선형 탐색을 차단했습니다. 이는 특히 간선이 많은 밀집 그래프에서 불필요한 CPU 사이클을 낭비하지 않도록 돕는 실전적인 최적화 기법입니다.

### 3. 구조적 설계를 통한 전략적 유연성 (Modularity)

탐색 로직과 상태 관리(`visited`, `edge`)를 `Dijkstra` 클래스로 **캡슐화(Encapsulation)** 하여 설계의 밀도를 높였습니다.

* **전략적 교체:** 객체지향적 설계를 통해 외부 인터페이스 수정 없이 내부 엔진(PQ ↔ Deque)만 교체하는 최적화 실험이 가능했습니다. 이는 준비된 구조가 신속한 성능 개선의 기회를 만든다는 것을 증명합니다.
* **자원 재사용:** 매 테스트 케이스마다 객체를 생성하지 않고, 선할당된 배열을 `init()` 메서드로 초기화하여 재사용함으로써 GC 부하를 최소화하고 런타임 안정성을 확보했습니다.

## 🧠 회고 및 결론

다익스트라에서 특정 지점까지의 최단 거리를 구할 때는 PriorityQueue를 적용하는 것이 최적이라고 알고 있지만, 본 문제에서는 특정 지점이 아닌 모든 지점까지의 최단거리를 구해야하기 때문에 Deque 활용하는 방법과 큰 차이가 없을 것이라고 생각했다. 실제로 PriorityQueue를 ArrayDeque 기반의 Queue로 변경한 후 테스트 해본 결과 생각보다 큰 차이가 난다는 사실이 놀라웠다.
