## 📌 문제 개요

사전(N개의 단어)이 주어졌을 때, 타겟 문자열 S를 한 글자씩 타이핑하는 과정을 시뮬레이션합니다. 각 단계마다 "현재까지 입력된 문자열을 접두사(Prefix)로 가지는 단어가 사전에 몇 개 있는지"를 실시간으로 출력하는 문제입니다.

---

## 💡 풀이 핵심 (Core Logic)

* **트라이 구조:** 사전 내의 단어들을 미리 등록해두고, 타겟 문자열을 한 글자씩 늘려가며 해당 시점의 접두사를 포함하는 단어 개수를 실시간으로 출력해야 함. 즉, Prefix Search와 Frequency Count가 동시에 이루어져야 하는 구조임

---

## 📊 트라이(Trie) 구현 방식별 비교

| 비교 항목 | 객체 기반 Trie | 2차원 정적 배열 Trie | 1차원 LCRS Trie (현재 방식) |
| --- | --- | --- | --- |
| **구조** | Node 객체 + Map/배열 | int[Node][26] | child / sibling 배열 |
| **메모리** | 매우 높음 (객체 오버헤드) | 높음 (26칸 고정 할당) | **매우 낮음 (2칸 고정 할당)** |
| **탐색 속도** | 보통 (포인터 추적) | **최상 ($O(1)$ 접근)** | 우수 (형제 노드 스캔) |
| **GC 부하** | 높음 (new 반복 호출) | **없음 (초기 1회 할당)** | **없음 (초기 1회 할당)** |
| **확장성** | 유연함 | 낮음 (배열 크기 고정) | **매우 좋음 (문자 무관)** |
| **추천 환경** | 일반 코테 | 메모리 넉넉한 환경 | **메모리 제한 엄격한 환경** |

## 🛠 성능 최적화 인사이트 - LCRS 트라이 구조의 이점

* **메모리 사용량 절감:** 일반 트라이는 각 노드마다 알파벳 개수만큼의 포인터 배열(int[26])을 가져야 하기 때문에 메모리 낭비가 심함. LCRS 트라이는 첫 번째 자식을 가지는 `child` 포인터와 바로 옆 형제를 가리키는 `sibling` 포인터 단 2개를 사용하면서, 메모리 낭비를 줄임

* **CPU 캐시 지역성 극대화:** LCRS 트라이는 자식을 찾기 위해 형제들을 순회해야하지만, 메모리 상의 데이터가 연속으로 배치도미. 따라서 캐시 히트율이 비약적으로 상승하여 빠르고 안정적인 속도를 보여줌

* **확장성:** 일반 트라이는 단어의 종류와 길이의 제약사항이 심함. 만약 대문자, 숫자, 특수문자가 섞인다면 배열 크기를 128 이상으로 늘려야 하므로 메모리 초과가 기하급수적으로 발생함. LCRS는 현재 노드의 문자만 검사하며 연결리스틀 타기 때문에, 문자의 종류나 길이에 상관 없이 동일한 메모리 구조와 로직을 유지할 수 있음

## 🧠 회고 및 결론

1. **효율성과 범용성 사이의 균형:** 본 문제는 단어 길이의 합이 200,000으로 일반 트라이 코드로도 충분히 통과 가능합니다. 하지만 범용성과 메모리 공간을 효율적으로 관리하기 위해서 난이도 있는 LCRS 코드 구현을 연습하

2. **구현 난이도:** 확실히 일반 트라이보다는 구현 난이도가 있는 편임. 아직은 완벽히 이해하지 못했으며, 문제를 더 풀면서 확실히 체득할 예정

3. **모듈화와 결합도에 대한 고민:** 이번 코드는 단순히 정답을 맞추기 위한 일회성 코드보다는, 역할이 명확히 분리되고 결합도가 낮은 코드를 작성하고자 노력했습니다.
   
   * Input class는 데이터 정제(Fast I/O)를 담당함
   * Trie class는 순수 비즈니스 로직(저장 및 탐색)을 담당함
