## 📌 문제 개요

사전(N개의 단어)이 주어졌을 때, 타겟 문자열 S를 한 글자씩 타이핑하는 과정을 시뮬레이션합니다. 각 단계마다 "현재까지 입력된 문자열을 접두사(Prefix)로 가지는 단어가 사전에 몇 개 있는지"를 실시간으로 출력하는 문제입니다.

---

## 💡 풀이 핵심 (Core Logic)

* **실시간 카운팅 (Prefix Count):** 단어를 삽입(`insert`)할 때 해당 경로에 있는 모든 노드의 `count` 변수를 1씩 증가시킵니다. 쿼리 시점에는 별도의 탐색 없이 해당 노드의 `count` 값만 읽으면 정답이 됩니다.
* **배열 기반 인덱싱:** `trie[node][char]` 구조를 사용하여 $O(1)$의 속도로 다음 노드로 점프합니다.
* **연속적 쿼리:** 검색어를 한 글자씩 늘려가며 탐색할 때, 매번 루트부터 시작하지 않고 **이전 탐색의 노드 위치를 유지**하며 한 단계씩 내려감으로써 전체 쿼리를 $O(M)$에 해결합니다.

| 비교 항목 | 객체 기반 Trie | 2차원 정적 배열 Trie | 1차원 LCRS Trie (현재 방식) |
| --- | --- | --- | --- |
| **구조** | Node 객체 + Map/배열 | int[Node][26] | child / sibling 배열 |
| **메모리** | 매우 높음 (객체 오버헤드) | 높음 (26칸 고정 할당) | **매우 낮음 (2칸 고정 할당)** |
| **탐색 속도** | 보통 (포인터 추적) | **최상 ($O(1)$ 접근)** | 우수 (형제 노드 스캔) |
| **GC 부하** | 높음 (new 반복 호출) | **없음 (초기 1회 할당)** | **없음 (초기 1회 할당)** |

| **추천 환경** | 일반 코테 | 메모리 넉넉한 환경 | **메모리 제한 엄격한 환경** |

## 🛠 성능 최적화 인사이트 (Performance Insights)


### **1. LCRS 구조의 평탄화(Flattening)를 통한 메모리 극대화**

* **일반 트라이의 한계:** 노드당 `int[26]` 배열(104바이트)을 할당하는 방식은 희소 데이터(Sparse Data) 상황에서 메모리 낭비가 심각합니다.
* **LCRS의 효율성:** `child`와 `sibling` 포인터 단 2개(8바이트)만 사용하여 노드를 구성함으로써, 일반 방식 대비 **메모리 사용량을 약 13배 이상 절감**했습니다. 이는 메모리 제한이 타이트한 환경에서 압도적인 생존력을 제공합니다.

### **2. CPU 캐시 지역성(Cache Locality) 극대화**

* **이론 vs 실제:** LCRS는 형제 노드를 탐색하는 $O(\Sigma)$의 선형 탐색 과정을 거치지만, **1차원 정적 배열로 평탄화된 메모리 구조** 덕분에 실제 속도는 비약적으로 빠릅니다.
* **캐시 히트율:** 데이터가 메모리상에 연속적으로 배치되어 현대 CPU의 **Prefetch 기능과 L1/L2 캐시 히트율을 극대화**합니다. 결과적으로 해시 계산 오버헤드가 있는 `HashMap`이나 파편화된 `Object` 구조보다 훨씬 빠르고 안정적인 성능을 보여줍니다.

### **3. 문자 집합 확장성 (Scalability)**

* **범용성 확보:** 알파벳 소문자에 국한된 `Node[26]` 방식과 달리, 현재 노드의 값만 검사하며 리스트를 순회하는 LCRS는 **대문자, 숫자, 특수문자 등 어떤 유니코드 입력에도 동일한 로직과 메모리 효율을 유지**할 수 있는 강력한 확장성을 가집니다.

## 🧠 회고 및 결론
 
### 1. 효율성과 범용성 사이의 균형

이 문제는 전체 문자열 길이 합이 제한되어 있어 일반적인 2차원 배열 기반 트라이로도 충분히 해결 가능합니다. 하지만 굳이 LCRS(Left-Child Right-Sibling) 구조를 선택한 이유는 실전에서의 범용성 때문입니다. 메모리 제한이 극도로 타이트한 환경이나 문자 집합의 범위가 넓은 고난도 문제에서도 흔들리지 않는 최적화된 풀이를 체득하고 싶었습니다.

### 2. 구현의 난이도

LCRS는 논리 구조를 1차원 배열로 평탄화해야 하므로 일반 트라이보다 구현 난이도가 높습니다. 실제로 구현 과정에서 포인터 관리 오류로 인해 시행착오를 겪기도 했습니다. 아직은 LCRS 구조에 익숙하지 않아 문제를 더 풀면서 확실하게 익힐 필요가 있을 것 같습니다.

### 3. 모듈화와 결합도에 대한 고민

단순히 정답을 맞히기 위한 일회성 코드보다는, 역할이 명확히 분리되고 결합도가 낮은 코드를 작성하고자 노력했습니다.

`Input` 클래스는 데이터 정제(Fast I/O)를 담당하고, `Trie` 클래스는 순수 비즈니스 로직(저장 및 탐색)에만 집중하도록 설계했습니다.

클래스 단위로 캡슐화하면서 코드의 길이는 다소 늘어났지만, 결과적으로 각 로직이 독립적으로 작동하는 '깔끔한 코드'를 얻을 수 있었습니다.
