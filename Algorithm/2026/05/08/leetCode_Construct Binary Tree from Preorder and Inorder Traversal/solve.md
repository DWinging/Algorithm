## LeetCode MID [Construct Binary Tree from Preorder and Inorder Traversal](https://leetcode.com/problems/construct-binary-tree-from-preorder-and-inorder-traversal/description/) (c++, Java)

> **날짜:** 2026년 5월 8일

> **언어:** c++, Java 8
> **핵심 키워드:** 트리, 분할 정복, 트리에서의 순회

---

## 📌 문제 개요

전위 순회(Preorder)와 중위 순회(Inorder)의 결과 배열이 주어졌을 때, 이를 분석하여 원래의 이진 트리(Binary Tree)를 완벽하게 복원하는 문제입니다. 트리의 순회 특성을 이해하고, 이를 바탕으로 정확한 인덱스 구간을 나누어 재귀적으로 서브트리를 재구성하는 논리적 탐색 및 분할 정복 능력을 요구합니다.

---

## 💡 풀이 핵심 (Core Logic)

### 1. 순회 특성을 활용한 루트 및 구간 분할

* **탐색 방향성 확보:** 전위 순회(Preorder)는 항상 현재 탐색 범위의 루트(Root)를 가장 먼저 방문하며, 중위 순회(Inorder)는 그 루트를 기준으로 **왼쪽 서브트리와 오른쪽 서브트리**를 명확히 양분하는 특성이 있습니다. 이를 결합해 루트를 확정하고, 자식 노드들의 범위를 쪼개는 방식으로 접근합니다.

### 2. 전역 인덱스(`rootIdx`)를 활용한 루트 추적

* **Zero-Allocation 복사 방지:** 재귀를 돌 때마다 배열을 새로 잘라(Slicing) 넘기면 불필요한 시간, 메모리 손실이 발생합니다. 대신 `rootIdx`(또는 `preIdx`)라는 전역(멤버) 변수를 유지하며, Preorder 배열에서 순차적으로 다음에 생성될 루트 값을 $O(1)$에 뽑아내도록 구조를 최적화했습니다.

### 3. HashMap을 통한 탐색 최적화 ($O(N^2) \rightarrow O(N)$)

* **선형 탐색 병목 제거:** 매번 Inorder 배열에서 루트의 위치(`mid`)를 찾기 위해 `for` 루프를 돌리면 최악의 경우 편향 트리에서 $O(N^2)$의 시간이 소요됩니다.
* 모든 노드의 값이 고유하다는 조건(Unique Values)을 활용해, 사전에 Inorder의 값을 키(Key), 인덱스를 값(Value)으로 하는 `HashMap`(C++의 경우 `unordered_map`)을 구성하여 위치 탐색 시간을 $O(1)$로 단축시켰습니다.

## 📊 핵심 인사이트 - 인덱스 기반 분할 정복의 정교함

배열의 일부분을 복사해서 넘기는 방식은 코드가 직관적일 수 있으나, 재귀 깊이가 깊어질수록 엄청난 오버헤드를 발생시킵니다. 반면, 인덱스(Start, End)만 넘기면서 원본 배열 하나만 참조하는 방식은 성능상 압도적인 이점을 가지지만, 그만큼 오프셋 계산에서 한 치의 오차도 허용하지 않는 **정교함**을 요구합니다.

특히 "왼쪽 자식 노드의 개수(`leftSize`)"를 구해 다음 재귀의 구간을 설정할 때, 기준점을 자칫 잘못 잡으면 메모리 침범으로 직결됩니다. 메모리를 아끼는 저수준 제어일수록 논리의 정밀도가 중요해집니다.

## 🛠 트러블 슈팅

### 1. C++ 리팩토링 중 인덱스 오버플로우 오타 (Out of Range)

* **문제:** 왼쪽 서브트리의 Preorder 구간을 지정할 때, 현재 범위의 시작점(`sPre`)을 기준으로 `sPre + 1 + left`가 되어야 할 공식을, 전체 끝점인 `ePre`를 잘못 섞어 `ePre + left + 1`로 작성해 범위를 크게 이탈함.
* **해결:** 변수명 오타(`s` vs `e`)로 발생한 런타임 에러임. 인덱스 오프셋을 현재 서브트리의 시작점 기준으로 정밀하게 교정(`sPre + left + 1`)하여 범위 초과를 해결함. 

### 2. Inorder 순차 탐색의 성능 병목 제어

* **문제:** 초기 C++ 코드에서 Inorder 구간 내의 `root` 위치를 매 재귀마다 반복문으로 찾아 성능 오버헤드가 존재함.
* **해결:** Java 8 코드로 최종 리팩토링하는 과정에서 `HashMap`을 도입하여 $O(1)$ 탐색으로 최적화. 복잡한 인덱스 계산 지옥에서 벗어나 코드의 간결함과 속도를 동시에 확보하여 구현 시간을 단축함.

## 🧠 회고 및 결론

문제의 로직은 간단하지만, 정교한 인덱스 계산과 기초 이해도를 요구하는 문제였습니다. 순차 탐색을 주로 사용해왔지만, HashMap을 활용하면 안정적인 성능을 얻을 수 있습니다.
